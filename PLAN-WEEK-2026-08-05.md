### D1 · Buy the domain, then submit Google OAuth verification + book CASA

Testing mode is now the front door for *everything*: with SSO-only, nobody can
create an account without you manually whitelisting them in Google Cloud
Console. This was already gating Gmail-connect; the deletion makes it gate
signup too.

**Buy the domain first — today, before submitting.** Google reviews a specific
config (redirect URIs, homepage, privacy policy URL). Submitting a cloudflared
tunnel hostname and then moving to the VPS next week means changing the thing
under review and restarting a 4–12 week clock.

A domain is ~$10 and permanent. Point it at the tunnel now and at the VPS next
week — Google reviews the hostname, and the hostname doesn't change when the
backend moves. One clock, no restart, and the VPS stays where it is in the
schedule.

Then:

- Update `GOOGLE_OAUTH_REDIRECT_URI`, `GOOGLE_LOGIN_REDIRECT_URI` and
  `PUBLIC_BASE_URL` to the new hostname, and register both redirect URIs on the
  OAuth client.
- Check whether narrower scopes clear the bar. `gmail.modify` is heavier than
  `gmail.send` + `gmail.readonly`; if the app works with less, the assessment
  is cheaper and faster.
- Budget: ~$540–1,000, 4–12 weeks of waiting.

**Done when:** domain registered and resolving, redirect URIs updated,
verification submitted, confirmation reference recorded in TODOS.md.

## Monday — delete password auth

One change, six parts. It removes more code than it adds.

### M1 · Delete the password paths

- `server.py`: remove `POST /signup` and `POST /login` handlers, `CredentialsBody`
- `auth.py`: remove `hash_password`, `verify_password`, `PBKDF2_ITERATIONS`
- `accounts_db.py`: remove `create_account`, `AccountLinkBlocked`, and the
  `by_email.get("password_hash")` branch in `link_or_create_google_account`
- `server.py`: drop the `login:` and `signup:` `ratelimit.check` calls with them

**Acceptance:** grep for `password_hash`, `verify_password`, `AccountLinkBlocked`
returns only the migration note. No handler accepts a password.

### M2 · `/login` and `/signup` survive as one-button pages

`require_auth` redirects unauthenticated users to `/login?next=…`, and the
marketing site's "Start free" points at `/signup`. Neither route can 404.

Both become the same thin page: one **Continue with Google** button. `/signup`
may simply 302 to `/auth/google/login`.

**Acceptance:** hitting `/outreach` logged out lands on a page with exactly one
control, and it works.

### M3 · Fix `?next=` — it needs a cookie, not callback parsing

Verified: `server.py:370` redirects to `/` or `/settings` and ignores `next`
entirely — but `next` **never reaches the callback**. `google_login_callback`
takes no such parameter, and `build_login_auth_url(auth.create_oauth_state())`
carries only an expiry-signed CSRF token. `auth.py:69-76` deliberately shapes
that token with one dot "so it can never be mistaken for a session token."

So don't widen the state token. At `/auth/google/login`, set a short-lived
`HttpOnly` cookie holding the validated `next` path; read and clear it in the
callback; fall back to today's `/` or `/settings` behaviour when absent.

Reuse the sanitiser already in `static/login.html:94` —
`/^\/[^/\\]/.test(next)` — server-side, so `//evil.com`, `https://…` and
`\\evil.com` are all rejected.

**Acceptance:** logged out → visit `/outreach` → Continue with Google → land on
`/outreach`, not `/`. A crafted `?next=//evil.com` lands on `/`.

### M4 · Delete the password-auth tests with the feature

Tests asserting on removed code are how a suite rots into "green but
irrelevant" — the state the smoke test already caught once, where 300-odd
passing tests coexisted with a dead-end flow and false copy.

**Acceptance:** report the count before and after. It should go **down**. A
smaller suite that tests live code beats a bigger one that doesn't.

### M5 · Sessions: shorten, and defer revocation on purpose

No password vector remains, and Testing-mode's 7-day token death self-limits any
stolen-cookie window.

- `auth.SESSION_TTL_SECONDS`: 14 days → 7 days
- No session store, no `session_version`. Adding one would turn
  `verify_session_token` from a pure HMAC check with zero I/O into a database
  read on **every request** through `require_auth`.
- Write it in TODOS.md as deferred **by decision**, with that reason, so the next
  audit doesn't file it as an oversight.

### M6 · The docs pass — part of the deletion, not a follow-up

This project's documented disease is copy drifting from code. A deletion without
the docs pass restarts it.

- `outreach-agent/README.md` — remove "sign up with a password"
- `.env.example` and schema comments — remove password-flow references
- `BUGS.md` — BUG-1, BUG-2 and BUG-3 are **already marked FIXED** (`:10`, `:61`,
  `:101`) — verified, not assumed. The deletion makes BUG-2 and BUG-3
  *vestigial* rather than fixed: the code paths they describe stop existing.
  Add one line to each saying so; do not re-open them.
- `TODOS.md` — close "Auth hardening: email verification + password reset";
  it's resolved by removing the thing that needed it

**Acceptance:** no document describes password signup.

## Wednesday–Friday — interviews

Five conversations minimum, split across both cohorts.

**Record for each:** which cohort, what they use now, would they switch (y/n),
**the number they name**, and the single biggest objection in their words.

**The finding is the price, not the opinion of the slogan.** Cohort A saying
"$15/mo" and Cohort B saying "$100/mo" are two different companies, and you learn
which one you're building this week instead of after building the wrong tier.

**Abort criterion, written before the data arrives:** if the dominant objection
is *"nice, but my tool has warmup"* rather than a price, the reshape isn't
finished — approval-first is a feature, not a wedge, and Layer 2's positioning
work should not start.

**And the free result:** if five cold-email practitioners won't answer a
one-sentence cold message in a week, that's the product's own premise returning
a verdict at no cost.
